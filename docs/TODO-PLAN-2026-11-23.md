## 2. P0 — 阻断性 / 安全相关

### P0-1 两个本地提交的归属处理（**最先做，其它都基于此**）
- **问题**：`main` 上有 2 个本机环境补丁提交（`b4cd220` archlint musl 补丁、`bb963c1` biome 修正），未推送。
- **为什么先做**：后续所有任务都从 `main` 开分支；这两个提交若留在 main 上，任何 PR 都会夹带无关改动。
- **可选方案**（需你拍板）：
  - (a) 长期保留 → 仍建议移到分支 `chore/dev-env-archlint-patch` 走 PR；
  - (b) 不作为仓库内容 → `git reset --soft origin/main` 撤回，补丁只留在本机（`postinstall` 会随撤回一起消失，需另记迁移说明）。
- **验收**：`git log origin/main..main` 为空或只剩本 PR 分支；`bun install` 后 archlint 仍可运行。

### P0-2 网关迁入 WSL systemd（TODO §3，**0/10 已完成**）
- **实测缺口**：`systemctl --user` 可用（systemd=true）、**无 llmveto unit**、8787/8790 端口空闲、dsh web 已在 3080 运行。
- **子项**：
  1. 建 `~/.config/systemd/user/llmveto.service`（`EnvironmentFile`、`LLMVETO_DAEMON_CHILD=1`、`Restart=on-failure`）；
  2. `LLMVETO_UPSTREAMS` 写入 `~/.config/llmveto/env`（`chmod 600`，**不进仓库**）；
  3. 生命周期口径写死：托管后用 `systemctl --user stop`，不用 `llmveto stop`；
  4. 实测 dsh → 网关一笔真实流量（canary / evidence / metrics）；
  5. `llmveto doctor` 检查 null drift。
- **验收**：`systemctl --user status llmveto` = active；`curl 127.0.0.1:8787/_llmveto/metrics` 返回 JSON；dsh 一笔对话在 `evidence.jsonl` 落记录。

### P0-3 ACP 客户端绕过网关的拍板（TODO §6 第一条）
- **实测**：`trae` / `codebuddy` 走 ACP 子进程直连供应商，canary / 命令扫描 / evidence **全不覆盖**。
- **这是安全缺口而非代码缺陷**：网关"受管路径"承诺对这两个 provider 不成立。
- **决策**：codebuddy 可试 `CODEBUDDY_BASE_URL` 改道（先做可行性验证）；trae 无覆盖项 → 接受风险并在 `docs/KNOWN-ISSUES.md` 明示，或放弃该 provider。
- **验收**：结论落文档 + README 边界声明同步（README 中英双份）。

### P0-4 `dangerous-command-scan` 集成测试补齐（TODO §6）
- **实测**：只有 `tests/unit/checkers/dangerous-command-scan.test.ts`，**无集成测试**（已确认）。
- **为什么 P0**：这是本机唯一在跑的响应侧安全检测器，单测不覆盖"真实网关 + mock upstream、非流式警告落链、响应照常返回"。
- **验收**：新增 `tests/integration/` 用例，覆盖 findings 落链 + `action_taken=warned` + 响应未被阻断。

### P0-5 Gate 8 detect-secrets 实际未生效（TODO §5）
- **实测**：`.secrets.baseline` **MISSING**；门禁目前实际只有 gitleaks 在跑。
- **风险**：门禁 PASS 不代表 detect-secrets 覆盖过 → 属"静默降级"。
- **验收**：生成 baseline 入仓；用**公认会被报的密钥夹具**做一次端到端对账（对应 #843），证明它真的拦截。

### P0-6 孤儿 tag `v0.4.0` 处置（TODO §5）
- **实测**：远端 tag 仍存在（`a3e0455`），npm 无 0.4.0 版本、无 Release。
- **做法**：保留 tag 并建 Release 标注 "superseded by v0.4.1, never published to npm"（**推荐**，无需放开 Ruleset）；或按原 TODO 删 tag（需先放开规则权限）。
- **验收**：GitHub 上该 tag 有明确说明，不再误导使用者。

## 3. P1 — 功能正确性与测试证据

### P1-1 canary 会话键漂移风险（TODO §6）· **建议紧跟 P0-2**
- dsh 不发 `x-llmveto-session-id`，走"首条 user 文本摘要"回退键（`src/canary/session-key.ts`）。
- **需实测**：抽样 dsh 真实请求历史形态，确认首条 user 消息不会被裁剪 → 否则会话键漂移导致 canary 漏判。
- **产出**：结论 + 若会漂移则给出修复方案。

### P1-2 canary 按 provider 归因（TODO §6）
- 现状：dsh 所有 provider 共用 `dsh/cliproxy` 单路由键 → 命中只知"来自 dsh"，**不能定位具体供应商**。
- **方案评估**：按 provider 拆路由（改 `LLMVETO_UPSTREAMS` + `MANUAL_CANARY_MANAGED_ROUTES`）。

### P1-3 canary 容量评估（TODO §6）
- registry TTL 24h / LRU 64；并发会话多会淘汰旧串。评估上调或按客户端分桶（**需同步改 spec 常量**）。

### P1-4 流式 warn 语义一致性（TODO §6）
- 流式路径 warn 只进 `findings`，`action_taken` 保持 `allowed`（`src/gateway/core.ts` D-11，已核实注释在 L710/717）。
- **这是已知语义差异，不是 bug**：要统一需单独评审并改 spec。建议先登记 KNOWN-ISSUES。

### P1-5 模型自述不一致的定性（TODO §7）
- `gemini-flash-lite` 自称 "GPT-4o (2024-05-13)"、`modelscope GLM-5.2` 自称 "GLM-4-9B"（两轮复现）。
- **决策**：保留观察 / 降级用途 / 从 dsh 移除。自述不能作证据，需结合 tokenizer 指纹或官方接口比对。
- **注意**：这正是本项目存在的意义（模型字段一致性），值得认真处理。

### P1-6 provider 探针批量探活（TODO §7）
- trae 17 个模型仅验过 1 个（15 个未验）；codebuddy 17 个仅验 1 个（16 个未验）。
- 需确认 hy4free 额度耗尽后的报错形态，**避免把额度耗尽误判为模型故障**。

### P1-7 探针基线固化（TODO §7）
- 把 `var/provider-probe-result*.json` 通过率与 p50 固化为基线文件，后续 `--repeat 2` 做漂移对比。
