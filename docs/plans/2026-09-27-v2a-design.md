## 2. 候选架构与 trade-offs

**候选 A（推荐）—— 网关编排 + 新域 `src/canary/**`，状态全部归 gateway/canary 层。**
checker 保持两态纯 reducer（TEST 契约 #2 不动一字）；跨会话状态（registry）、注入、窗口存储、预算、admin 端点全部由 gateway 层持有，经 `ScanUnit.meta`（只读快照）与 `ScanWindow.extra`（checker 私有累积态）进入 checker 视野。
代价：gateway 层改动面最大（`core.ts` / `server.ts` / `scan-unit.ts` 三处签名演化）；canary 域约 370 LOC 新代码。

**候选 B —— checker 内部模块级单例状态。** `tool-call-shape` / `canary-return-scan` 各自持模块级 Map 存跨会话/跨片状态。省约 400 LOC、签名零改动。
否决理由：直接违反 TEST 契约 #2（checker 不得读环境外状态）——fixture 无法复现、并行测试互染；`architecture.yaml` 的 checkers 层语义（"不知道网关存在"）被架空；轮换/在途快照语义（需求 §4.3）在 checker 内无处安放——它们是请求生命周期概念，不是扫描概念。

**候选 C —— 独立 registry sidecar 进程。** canary 状态与轮换由第二个常驻进程持有，网关经 loopback IPC 查询。隔离最彻底，CLI 双写竞态天然消失。
否决（本期）：多一个常驻件，破坏 DESIGN §组件 的单进程 daemon 形态与 v1 部署验收结论；v2a 的匹配域（64 session / 24h / 单机）规模用不上一台独立进程。**留档**：v2b 引入 provider 信任分与巡检时若状态面继续膨胀，重评。

## 3. 推荐方案：三条主时序

**时序 1 · 请求注入**（`server.ts:dispatch` → `core.ts:handleChatCompletions`）
1. `dispatch` 拦截 `/_llmveto/*` admin 路由（D-03），其余照旧走身份识别（`server.ts:132-136`）与路由解析。
2. `scanRequest` 在**注入前**的原始体上跑（判定域 = 用户实发字节；这同时保证 canary 不会成为 `egress-secret-scan` 的误报源——FP=0 判定域不被注入污染）。
3. `reqDecision.action === "block"` → 照旧 502，不注入（§4.4"已过闸"）。
4. 过闸后：`deriveSessionKey`（D-06）→ `canary.allocate(key)`（缺则就地分配并落 registry，§4.3）→ `inject(body, canary)` 按 §4.4 六分支只增不改 → 以**注入后**的体 `fetch` 上游。
5. `handleChatCompletions` 返回值新增 `forwardedBody` 与 `canaryMeta`；`writeEvidence` 的 `request_bytes` / `request_body_sha256` 记录注入后体（D-04）。

**时序 2 · 响应流窗口**（`core.ts:scanResponseStreamChunk` 重写）
1. 每连接持 `Map<checkerId, ScanWindow>`（D-07）；进入 checker 循环前，网关对每个有状态流式 checker 以 `unit.text.length` 推进其 cursor **一次**。
2. checker 收到 `(自己的 window, unit)`，回传 `[result, window]`；网关**忽略**回传 cursor、**保留**回传 `extra`。
3. 预算包裹（D-09）在每次 checker 调用外层，事后判定。
4. `flattenFindings` 消费 error（D-10）；policy 决策照旧；命中 block → `encodeVetoEvent` 终止流（幂等性由现单遍 generator 结构保证，AC-V2a-20）。

**时序 3 · error 落链**
checker 层 `reason` → `flattenFindings` 产出 `findings[]` 内 `verdict:"error"` 条目（§4.5 落点表）+ `AppendInput.reason` 顶层可选位（key-absent 语义，§14.4-4 的 canonicalJson 结论）；网关自身行为（`registry_unavailable` / `inject_skipped`）只写顶层位、不产条目。

## 4. 关键设计决策

**D-01 · 状态归属 = 候选 A。** `src/canary/**` 为新层（`architecture.yaml` 增列，`allowed_imports: [shared, canary]`；gateway 可 import canary；cli 只可 import canary 的读侧——见 D-03）。checkers 层 `allowed_imports` **不变**（仍 `[shared, checkers]`），并由 `architecture-boundaries.test.ts` 断言 checkers 不 import canary（AC-V2a-19③ 静态侧 + AC-V2a-26④ 不放宽）。

**D-02 · registry 存储形态。** `stateDir/canary-registry.json`（与 `gateway.pid` 同级，`cli/index.ts:36` 的 stateDir 解析），schema 自带 `version` 字段。唯一写者 = 常驻网关；写序 = 写 tmp 文件 + `renameSync`（同卷原子，崩溃残留只能是旧完整文件，无半行）。加载时校验：非法 JSON / 版本不识 / 结构不符 → 按 §4.3 转为 `registry_unavailable`（不注入不匹配 + 顶层 reason + 计数，不得静默）。淘汰 = 惰性（加载时 + 每次写入时按 lastSeen 排序，TTL 24h 与 LRU 64 先到为准）。

**D-03 · 控制通道。** `POST /_llmveto/canary/rotate`：`dispatch` 在**路由解析之前**拦截 `/_llmveto/*` 前缀（否则会落入 catch-all → 502 + 污染 evidence 链），不经 checker/policy，不产生 evidence 记录（非受管路径）。网关运行时 CLI 经此端点轮换并等待确认。**网关未运行时**：CLI 写标记文件 `stateDir/canary-rotate.request`，网关下次启动时消费并执行轮换——这**替代**需求 §4.3"网关未运行时才直接落盘"的许可，理由：让 AC-V2a-19③ 的"CLI 无写能力"静态断言能在层粒度成立（cli 不 import `src/canary` 的写侧），不需要把写逻辑复制进 CLI。属对 §4.3 一句许可的**窄化**，列入拍板项 #B。**标记文件生命周期 [R2 A-m4/T-m2]**：CLI 侧写 tmp + `renameSync`（与 D-02 同一原子写法）；网关启动序 = 读标记 → 执行轮换 → **成功后删除**标记文件；删除失败 → 下次启动重复轮换（轮换幂等：重新生成串并整体替换匹配域，重复执行只多耗一次熵，不破坏状态——已接受残留语义）；标记内容非法 → 忽略 + 删除 + `doctor.canary-registry` 计数，不得静默。**轮换历史不进链 [R2 A-m5]**：控制面非流量面，取证依赖 registry 的 `rotation_count`/`last_rotated_at` 与 `status`/`doctor` 展示——这是已登记的取证取舍，不是遗漏。
**已知滥用面（诚实登记）**：loopback 信任域内无认证，任何本机进程可反复 rotate → 匹配域被清空 = 检测覆盖降级（§7 P4 同族）；**离线标记文件同理 [R2 A-m4]**——本机任意进程可写 `canary-rotate.request`，与 loopback rotate 同属一个信任域滥用面，缓解相同：不认证、靠可观测。缓解不是认证而是**可观测**：registry 内持久 `rotation_count` + `last_rotated_at`，`status`/`doctor` 展示，doctor 对短窗口高频轮换告警（告警阈值定值：滚动 60s 内 >3 次 rotate 即告警，写入 fixture 常量表可注入）。
**熵源可注入**：registry 与注入的随机性经构造参数注入（生产默认 `node:crypto randomBytes`），fixture 用固定熵获得确定性 canary 串——TEST 契约 #1 精神的延伸，使 AC-V2a-06/07/08 可表驱动。

**D-04 · 注入点与 evidence 语义。** 注入在 `handleChatCompletions` 内、block 判定之后、`fetch` 之前（`core.ts:135-146` 之间）。`request_bytes` / `request_body_sha256` 记录**注入后**的体 = 上游实收的外部事实；原始体无信息损失（`B' = B[0..k] + canary + B[k..]`，canary 可由 `session_id` → registry 反查恢复）。对照方案（记注入前体）会让链与上游日志对不上账。列入拍板项 #A（它改变 v1 冻结字段在注入请求上的语义，虽然 `REQUIRED_FIELDS` 不变）。
**取证边界（诚实披露 [R2 A-M2/T-M1]）**：上述"反查恢复"依赖 registry 的**有界留存**——TTL 24h / LRU 64 / 轮换即作废旧串 / registry 损坏转 `registry_unavailable` 后重写。超窗之后，仅凭链上 `request_body_sha256` 无法还原原始体 B（canary 串已不可查）；AC-V2a-07 的不变式是**测试期**断言（fixture 现场构造、现场验证），不是"任意时限内可恢复"的承诺。此边界登记进 §9 风险表，属 #A 披露义务的一部分。

**D-05 · 匹配域快照。** `meta.canary_candidates` = 请求进入时活跃集合的只读快照，**排除请求方自己的 canary**（Q3"单请求内复述显式判不命中" + AC-V2a-06 负样本的实现面）；`canary-return-scan` 只读该快照，持快照判在途请求（§4.3 轮换快照行，AC-V2a-08/19②）。明文不进链由既有 `body_capture=metadata_only` 咽喉点保证（AC-V2a-06 的 grep 断言）。

**D-06 · 两套会话键并存。** 新增 `src/canary/session-key.ts`：`deriveSessionKey(headers, body)` = 头优先（`x-llmveto-session-id`）→ 回退 `sha256(len:text 串接的首条 user text parts)` 前 16 字符（§4.3 定值，非 text part 不计入）。**命名 [R2 A-m3]**：函数名取"会话键"以对齐 §4.3 与 AC-V2a-17 的用词（"同会话两次请求 canary 相同"），不用"conversation"——CONTEXT.md 术语表的 Avoid 列明示回避该词；与 evidence `session_id` 的派生（`server.ts:135`）是两个名字两个语义位，后者**不动**——改它会动 v1 冻结语义与既有验收；代价：缺头时 evidence `session_id` 是 per-request 而 canary 会话键是 per-conversation，两者语义不同属有意为之，注册为设计事实。头名复用既有 `x-llmveto-session-id`（§10.1-10 的拍板默认），AC-V2a-17 的字面 `x-llveto-session` 是占位名，定案后同批订正该 AC 文字——该订正**并入 `doc-consistency.test.ts` 的 grep 断言域**（连同 #B/#C/#D/#G，防占位名漂移）[R2 T-m1]。

**D-07 · 窗口归属（ADR-0005 / REQ-V2a-15 的实现）。** `scanResponseStreamChunk` 签名改为 `(windows: ReadonlyMap<string, ScanWindow>, chunkData, ...)` → `{ inputs, nextWindows, parsed }`；`handleChatCompletions` 以局部 `Map` 持有（per-request 生命周期，非全局）。网关权威推进一次 cursor；回传 cursor 忽略、回传 `extra` 保留进各自窗口。AC-V2a-25（经网关 offsets 等值）与 AC-V2a-26（隔离 + extra 存活）是其判定面。

**D-08 · offsets 计量单位钉死为 UTF-16 code unit index。** 理由：与 `String.indexOf` 定位语义一致，取证时可直接在响应原文上复现；v1 checker 命中集全 BMP，故"码点偏移"文字在 BMP 域内与 code-unit 等价（`invisible-unicode-scan.ts:49-51` 的注释已作此声明）。新增实现侧断言：fixture 含 1 例 astral 字符（如 `U+1F600`）先于命中出现，钉死期望值为 code-unit 口径——防"码点/code-unit"两种读法静默漂移。列入拍板项 #G（AC-V2a-25 的"全局码点偏移"文字需按此口径加注）。

**D-09 · 预算门（REQ-V2a-12 + AC-V2a-27）。** 新增 `src/gateway/budget.ts` 作为**唯一档位常量源**：`G3_TIER_8KB/32KB/512KB`（20/50/120ms，引用 DESIGN §性能预算数值）与 `G1_PER_CHUNK`。`GatewayConfig.checkerBudgetMs?: ReadonlyMap<string, number>` 注入口；`runWithBudget(fn, unit, budgetMs)` 以 `performance.now()` **事后**判定（同步 JS 无法抢占纯函数，语义=裁决面非止损面，§5 第五处）：超时 → 该 checker 结果改写为 `{verdict:"error", evidence:[], reason:"checker_timeout"}`，走 D-10 双层落链；**改写只替换 result，不吞 checker 回传的窗口**——流式下窗口照常按片推进与保留 `extra`（AC-V2a-27④ 的"窗口仍按片推进"由本句钉死）[R2 A-m1]。默认配置下三条路径（请求体 / 非流式响应体按 G3 分档、流式每 chunk 按 G1 门）全部接线；档位名被 fixture 常量表**引用**而非复抄（AC-V2a-12/27① 同源要求）。G-PERF 实测确认新 checker 集合在各档内成立，属门关闭判据（§14.5-3 的反向风险：第一次接门会把"慢但放行"变阻断）。

**D-10 · error 双层落链 + 顶层 `reason` 单值确定性规则。** `flattenFindings`（`core.ts:241-257`，现只遍历 `result.evidence`）扩展：对 `verdict==="error"` 的输入另产一条 `{checker, threat, verdict:"error", rule_id:<reason>}`（threat 按 §4.5 约定表：tool-call-shape→T2a、canary-return-scan→T1a）。顶层 `reason` 单值规则（多条并发时必须可判定）——**网关侧描述值优先于 checker error [R2 T-C1/A-M1 订正]**：`registry_unavailable` > `inject_skipped` > checker error reason（固定序 `window_overflow > checker_timeout > scanner_error > input_malformed`；同序位多条时按 `src/gateway/registry.ts`（checker 注册表）的声明序取第一条）。**为什么网关值优先**：§4.3 与 AC-V2a-19① 对"registry 不可用 → 顶层 `reason="registry_unavailable"`"的承诺是**无条件**的，不预设"该请求恰好没有 checker error"；checker error 的 reason 已由 `findings[]` 条目**全额保全**（D-10 双位中的 findings 位），顶层让位**无信息损失**；反过来若让 checker error 抢占顶层，则组合场景下 `registry_unavailable` 在链上**无处可落**（它按 §4.5 不产 findings 条目）= 覆盖降级被静默吞掉，违反 §4.3"不得静默"。此规则不触碰 AC-V2a-12 的断言面：其 fixture 场景中 registry 正常（无网关侧描述值并发），顶层 reason 仍取 checker 值。无任何异常时顶层 `reason` **整键不写**（不得 `null`——§14.4-4）。`AppendInput.reason?: string`；`validateEvidence` 增加 reason 词汇域校验（§4.5 六值 + 可缺席），契约 #4 的 26 项必填表不动（AC-V2a-23① 全等断言从 `EvidenceRecord` 键集派生）。

**D-11 · 观测类降级可达（AC-V2a-11）。** `decide()` 返回值增加 `degraded: boolean`（任何观测类输入 `verdict==="error"`——含超预算被 D-09 改写——即真）。`action_taken` 优先序：`blocked_before_forward` / `blocked_before_deliver` / `terminated_after_delivery` > `degraded_observational` > `warned` > `allowed`。**落链无分类豁免 [R2 A-M1/T-m3 订正，撤销本文 R1 稿的观测类抑制条款]**：全部 checker error——安全类与观测类、含被 D-09 改写的超时——同走 REQ-V2a-13(c) 的双位落链。依据：AC-V2a-24② 对 `scanner_error`/`input_malformed` 的"顶层 `reason` 与 `findings[]` 条目**同时出现**"断言**无分类限定**，AC-V2a-11 只断言 `action_taken` 不涉 findings 内容；§4.5 表 `checker_timeout` 行产生层列的"安全类"标注描述的是 v1 现状下该值的出现面，不构成落链豁免。**裁决语义不变**：`decide()` 不读顶层 `reason`、不读 findings 序列化结果，落链位不改变任何 action——观测类 error 照旧只降级不阻断。若未来要让某类 error 不落链，须先改 REQ-V2a-13(c)/AC-V2a-24②，不得在实现层静默豁免。

**D-12 · `declared_tools` 来源与无声明漏检。** dispatch/handleChatCompletions 从请求体提取 `tools[*].function.name` 与 `parameters.required`，经响应扫描单元 `meta.declared_tools` / `meta.declared_required` 下传（这同时是 REQ-V2a-01 让 `invisible-unicode-scan` 覆盖 tool-call 参数路径的管道：`buildResponseScanUnit` 把 `delta.tool_calls[*].function.arguments` 文本并入 `unit.text` 并在 meta 保留结构）。**无声明即漏检**：`declared_tools` 为空时"未知工具名 / 缺 required 参数"两子规则不适用（仅余 arguments JSON 有效性判定），否则 benign 语料上无法保证 FP=0（AC-V2a-03）。该漏检须登记进需求 §7 P4 第⑦条——只扩披露不扩能力，列入拍板项 #C（需求文档的一次增补）。
**FP=0 的负样本义务 [R2 T-M3]**：AC-V2a-03 的 benign 语料必须含**两类**不误报样本，缺一 FP=0 断言即未覆盖：① 未声明 `tools` 但响应含合法 `tool_calls`——断言"未知工具名/缺 required"两子规则不适用、整体 `clean`；② 已声明 `tools` 且响应 `tool_calls` 合法（JSON 有效、工具名在声明集内、required 齐全）——断言 `clean`（arguments JSON 有效性子规则不得误伤合法调用）。对应 adversarial 正样本（未知工具名 / 缺 required / 非法 JSON）各 ≥1 条已在 AC-V2a-01/02 域内，负正同批进 `tests/fixtures/` 表驱动。
