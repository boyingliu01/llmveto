### P0-3 ACP 客户端绕过网关的拍板（TODO §6 第一条）· **2026-11-23 复核后降级为「登记」**
- **机制**（已核实 `~/.dsh/profiles/web/cordis.patch.yml`）：网关靠改写客户端 `baseURL` 插在中间；普通 provider 有 `baseURL` 可改，而 trae/codebuddy 是 **ACP 子进程**，配置里只有 `command: /home/bull/.local/bin/traecli` + `args: [acp, serve]`，**没有 baseURL**。dsh 与它们用管道通信，流量根本不走 HTTP → 网关看不见。

## 3. P1 — 功能正确性与测试证据

### P1-1 canary 会话键（TODO §6）· **2026-11-23 已诊断，发现问题与原假设相反**
- **原假设**：客户端裁剪历史导致首条 user 消失 → 同会话内键漂移。
- **实测（13 个真实 dsh 会话记录，非模拟）**：
  - 同会话内跨轮漂移：**不发生** ✅（30 轮同键，dsh 历史累积从不删首条）；
  - **不同会话撞键：发生** ❌ —— 6 个不同会话共享键 `54442a56dc3a791e`。
- **根因**：dsh 把「系统注入类」消息也标成 `role: "user"`（`user-approval` / `runtime-context` /
  `model-selection` / `<system-reminder>` 等），这些消息文本对所有会话相同；当会话首条恰好是它们时，
  回退键 = sha256(首条 user) 就会碰撞。
- **影响**：`AC-V2a-17` 要求「异会话键不同」→ 当前违反第 1 条。后果是这些会话共享同一把 canary，
  **彼此之间的跨会话泄漏无法检测**。
- **修复方向已验证**：取「首个真实用户消息」→ 10 个会话 10 个唯一键。障碍是 `source.kind` 是 dsh 私有
  元数据，网关在 HTTP 体里看不到。
- **两条路径**（需决策）：A) 用 dsh 的 `request-headers` 钩子注入 `x-llmveto-session-id`（走 spec 设计的头优先路径，
  改配置不改代码）；B) 项目侧按文本特征跳过注入类消息（不依赖客户端，但脆弱）。
- **已修复（路径 A，2026-11-23）**：新建 DSH 插件 `~/.dsh/plugins/llmveto-session-header`，
  监听 `llm-pi-ai/request-headers`，把 DSH 的 sessionId 写入 `x-llmveto-session-id`。
  真实 dsh 流量验证：7 条请求全部带头，两个会话两个不同头，同会话恒定；
  用真实头复算网关键：修复前撞键 `54442a56…`，修复后各会话唯一。项目代码无需改动。
- **详见**：`docs/CANARY-SESSION-KEY-DIAGNOSIS-2026-11-23.md`

### P1-2 canary 命中归因（TODO §6）· **2026-11-23 已完成（实现"谁串进了谁"）**
- **原 TODO 假设**：dsh 所有 provider 共用 `dsh/cliproxy` 单一路由键 → 无法定位具体 provider；
  建议按 provider 拆路由。
- **实测修正**：拆路由不是关键。真正的归因缺口在**证据层**——canary 命中时只报
  `rule_id=canary-detected-in-response`，不记录**是哪个会话的 canary 串入的**。即使拆了路由，
  也只能知道"哪个 provider 的响应被污染"，仍不知道"谁污染了它"。
- **实现**（不改 spec 常量、不改 evidence_version）：
  - `CanaryStore.snapshotWithOrigin()`：与 `snapshot` 同集合同排除语义，额外保留来源会话键；
  - `canary-return-scan` 命中时写入 `Finding.origin`；
  - `EvidenceFinding.origin` 可选位，`validateEvidence` 的字段验证器模型不拒绝新增字段 → v1 链语义不变。
- **⚠️ 关键教训**：本次改动经过**两个逐字段/逐键构造的静默丢弃点**，两处都不被类型检查或既有单测发现：
  1. `toEvidenceFinding()` —— 不显式传递 → finding 丢 origin；
  2. `responseMetaFor()` —— 不并入 meta → checker 根本读不到归因快照。
  实测记录：只改 ① 时端到端断言 `origin=undefined`，正是漏了 ②。
  两处均已用集成测试锁死（反向探针：删任一处 → 测试变红）。
- **验证**：`tests/integration/canary-origin-attribution.test.ts`（真实网关 + 会泄漏的 mock upstream）
  断言 `origin=session-alpha`；另含「无泄漏时不出现 origin」与「带 origin 的记录仍通过官方
  `verifyEvidenceFile`」两条护栏。共新增 12 个测试（6 checker 单测 + 3 store 单测 + 3 集成）。
- **注**：`dsh/cliproxy` 路由拆分仍是可选优化，但它解决的是 provider 维度，与本条解决的会话维度正交。

### ~~P1-5 模型自述不一致~~ → **降级为 P3 观察项（2026-11-23 实测证伪）**
