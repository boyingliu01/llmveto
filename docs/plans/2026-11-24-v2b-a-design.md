## 1. 问题陈述

网关当前的扫描单元只认识一种线上格式（OpenAI Chat Completions）。三个目标客户端里：

- **promptfoo** 可配成 Chat 形态 → 走既有路径，是**低风险对照项**；
- **Claude Code** 说 Anthropic Messages（`POST /v1/messages`）；
- **Codex** 说 OpenAI Responses（`POST /v1/responses`，`wire_api="responses"` 是唯一支持值）。

后两者在当前实现下**几乎完全不可见**。已复现的后果（不是推断）：

```
POST /claude/anthropic/v1/messages (body 含 sk- 形态凭据) -> HTTP 200, action_taken="warned"
POST /codex/openai/v1/responses    (body 含 sk- 形态凭据) -> HTTP 200, action_taken="warned"
```

阻断类 checker `egress-secret-scan` 本应 `blocked_before_forward`，实际凭据已出境。
同时 `opencode/anthropic` 自 v1 起就是这么"受管"的，本机 0 流量所以没人发现。

**所以本 sprint 的工程目标是：让协议线格式成为网关的一等概念，而不是"if 分支写在投影函数里"。**

## 2. 总体方案

### 2.1 三维分解（不要混为一谈）

| 维度 | 是什么 | 落在哪 | 本 sprint 的约束 |
|---|---|---|---|
| **线格式（wire format）** | 请求/响应的线上 JSON 形态 | `src/gateway/protocols/` | 新增 `chat`（既有）、`anthropic-messages`、`openai-responses` |
| **线格式路由（wire route）** | 客户端把请求打到哪个路径前缀 | `src/gateway/server.ts` 的 `parseRoute` | 新增 `WIRE_ROUTE_PREFIXES` 映射，前缀 → 期望线格式 |
| **客户端（client）** | 谁在发请求、怎么配 | `src/adapters/` | 新增 `claude-code` / `codex` / `promptfoo` 三个适配器 |

**两维分开是 R1 结论（D5）**：R1-R2 两席都指出"客户端 ≠ 线格式"，promptfoo 一个客户端可走两种格式。
三个新前缀互不冲突，且**不改动**既有 `opencode/*`、`delphi/*`、`dsh/*` 的行为。

### 2.2 数据流

```
client ──▶ server.parseRoute ──▶ [wire route → expected format] ──┐
                                                                  ▼
                                    core: recognize(body) ──▶ known / known_but_empty / unknown
                                                                  │
              known ──▶ projectRequest(unit) ──▶ checkers ──▶ policy ──▶ forward(原始 body 逐字节)
                                                                  │
              unknown / known_but_empty ──▶ reason 码 ──▶ [受管路由: block] / [非受管: 覆盖降级]
                                                                  │
              response: 非流式 = 整体 body；流式 = 逐帧 SSE ──▶ projectResponse
```

**关键点：投影永远不改动转发字节。** 网关把**客户端原始 body** 交给上游（`request_bytes` /
`request_body_sha256` 的既有语义只对 canary 注入生效），投影只用于判定。

### 2.3 协议注册表（D5 的落地形态）

**R2 评审的两个 CRITICAL 共同指向同一件事：识别与覆盖判据都没有独立 oracle。**
因此这里把"权威清单"变成**协议自己声明的数据**，投影器去核对它，而不是投影器自证。

```ts
// src/gateway/protocols/types.ts
export type WireFormat = "chat" | "anthropic-messages" | "openai-responses";

/** 一个协议的"已知载荷字段"权威清单：覆盖判据的 oracle。 */
export interface CoverageSpec {
  /** 请求/响应里出现即算"该协议载荷"的键路径（点号路径，数组用 [] 表示）。 */
  readonly requestPayloadPaths: readonly string[];
  readonly responsePayloadPaths: readonly string[];
  /** 该键路径"出现即已覆盖"或需要投影（投影器必须报告处理结果）。 */
  readonly requiredProjections: readonly string[];
}

export interface WireProtocol {
  readonly format: WireFormat;
  readonly coverage: CoverageSpec;
  /** 某个已知载荷路径该由哪个投影器处理（null = 该路径在本文档 §1.1 明确不扫）。 */
  readonly handlerFor: (path: string, direction: "request" | "response") => string | null;
  /** 非流式投影：返回片段与"派生"标记，并**逐路径报告是否处理**。 */
  projectRequest(parsed: Record<string, unknown>): Projection;
  projectResponse(parsed: Record<string, unknown>): Projection;
  /** 流式：一帧 SSE data 的投影；无载荷返回空片段（不是错误）。 */
  projectFrame(parsed: Record<string, unknown>): Projection;
  readonly canaryInjection: boolean;
}

export interface Projection {
  readonly parts: readonly string[];
  /** 派生文本（对象规范化 JSON 等）：其 offsets 不指回原文（REQ-05）。 */
  readonly derived: boolean;
  /** 本次投影实际处理过的载荷路径（与 coverage 比对得到部分覆盖）。 */
  readonly handled: readonly string[];
  /** 原 body 中**存在**的已知载荷路径。 */
  readonly present: readonly string[];
}
```

**`shape_partial_coverage` 的判定不再靠投影器自证**：
`partial = present \ handled` 非空即部分覆盖。`present` 由 `coverage` 清单在**原始 body**上求得，
`handled` 由投影器逐路径上报，二者是独立来源。

### 2.4 识别：**路由权威 + 内容吻合**（R2 CRITICAL-1 的修正）

**R2 评审实测抓到的硬伤**：上一版用"特征键"让 chat 与 anthropic 互相竞争，而

```
Chat 标准请求      chat=true anthropic=true → 歧义 → unknown → BLOCK
Claude(带 system)  chat=true anthropic=true → 歧义 → unknown → BLOCK
Claude(无 system)  chat=true anthropic=true → 歧义 → unknown → BLOCK
```

在 DR-031（直接 fail-closed）下，这会**阻断目标客户端自己的全部流量**——即 §1 事故的翻版。
根因是：Claude 的"无 system、纯文本"请求与 Chat 请求**在结构上本来就无法区分**，任何纯内容识别都必然二选一或判歧义。

因此识别改为两层，**路由优先**：

| 层 | 规则 |
|---|---|
| ① 路由权威（`WIRE_ROUTE_PREFIXES`） | 命中已知前缀 → 该前缀**直接决定**线格式，不参与"投票"。`anthropic/*` → `anthropic-messages`；`codex/*` → `openai-responses`；`chat/*`、`openai/*`、`opencode/*` → `chat` |
| ② 内容吻合（仅在无权威前缀时） | 用 §1.1 矩阵中**互斥的**判别键：`input`/`output`/`instructions`/`object:"response"` → responses；块数组 `system` 或 `tool_use`/`tool_result` → anthropic；`choices` → chat；其余（同为 `messages` + 纯文本）→ **chat**（倾向已支持格式，而不是判未知） |
| ③ 兜底 | 既无权威前缀、又不含任何已知键 → `unknown` |

**关键性质**：`unknown` 从此只可能出现在"真正无法归类的 body"上，不会因为两种格式长得像而触发。
②的"其余 → chat"有明确代价，写进残余风险：**一个匿名路由上、纯文本、无 system 的 Anthropic 请求会被当作 chat 处理**，
其 `tool_use` 仍会被识别（若有），故只有"纯文本 + 无 system"这一最平凡形态受影响。

## 3. 详细设计

### D-01 扫描单元改动（`src/gateway/scan-unit.ts`）

**改动方式：加分支，不改既有分支。** 既有 `collectMessageParts` / `collectChoiceParts` 的输入输出
逐字节不变（由 §3 的对照测试锁死）。新增：

- `buildRequestScanUnit(body, parsed, headers, transport, outcome?)`：识别为 `anthropic-messages` 时，
  额外收集：`system` 的字符串或块数组内 `text`；`messages[].content[]` 中 `tool_use.input`（对象 →
  `JSON.stringify`，标 derived）与 `tool_result.content`（字符串或块数组）。
- 识别为 `openai-responses` 时，额外收集：`instructions`；`input`（字符串，或数组中的 `input_text.text` /
  `function_call.arguments` / `function_call_output.output`）；`output[]` 中 `output_text.text` 与
  `function_call.arguments`。
- `buildResponseScanUnit`：非流式形态补 `content[]`（anthropic）与 `output[]`（responses）。
- 流式：新增 `projectFrame` 分支（anthropic `content_block_delta.delta.text|partial_json`，
  responses `response.output_text.delta|delta`、`response.function_call_arguments.delta|delta`、
  `…done` 汇总帧里的完整 `arguments`）。

**为什么不是"再判断一次 `if (body.input)`"**：那样识别逻辑会散落在三个函数里，退化的正是 R1 三席担心的形态。

### D-02 处置的**两轴**判据（R2 CRITICAL-2 的修正）

上一版把"识别结果"与"覆盖结果"揉成一张四态表，导致 `known_but_empty` 不可达、
`shape_partial_coverage` 与它重叠、零文本部分覆盖落入四态之外。改为**两个正交判定轴**：

**轴 1：识别结果**（§2.4）——`known(format)` 或 `unknown`。只有两个值。

**轴 2：覆盖结果**（`coverage` oracle × 投影器上报）——对已完成识别的请求/响应体：

| 覆盖结果 | 定义 | `reason` | 受管路由 | 非受管/匿名 |
|---|---|---|---|---|
| `full` | `present \ handled` 为空 且 `present` 非空 | 不写 | 正常判定 | 正常判定 |
| `partial` | `present \ handled` 非空（**不论有没有文本**） | `shape_partial_coverage` | **block** | 覆盖降级 + 写 reason |
| `vacuous` | `present` 为空（该协议已知载荷路径一个都没出现） | `shape_known_empty` | **block** | 覆盖降级 + 写 reason |
| （轴 1 = `unknown`） | 无法归类 | `shape_unrecognized` | **block** | 覆盖降级 + 写 reason |

**这样三个问题同时消失**：
- `vacuous` 可达：一个只含 `model`、没有任何 `messages`/`input`/`system` 的 body，就是"协议已知（由权威前缀决定）但无载荷"；
- `partial` 覆盖零文本：判据是**路径集合差**，与文本量无关，所以"凭据藏在未投影字段、其余为空"也必然落 `partial`；
- 不再有"互斥"措辞：两轴独立相乘，同一条请求只有一个格。

**响应侧不再是"一律允许空投影"**（R2 指出的空洞）：响应同样跑两轴。空投影只有两种情况：
(a) `present` 为空 → 但流式心跳/`ping` 帧**不进两轴判定**（帧类型在 `projectFrame` 里先行分流，
不计入 `present`）；(b) `full` 且载荷为空 → 正常。

**reason 封闭枚举（四个码，与 `registry_unavailable`/`inject_skipped` 并列）**：
`shape_unrecognized` / `shape_known_empty` / `shape_partial_coverage` / `inject_skipped`。
`full` 不写 reason。非受管路由**同样写 reason**（不留"静默 allowed 且无 reason"）。

### D-03 路由前缀与"受管路由"的**定义**（R2 MAJOR-4 的修正）

上一版用线格式名作前缀（`anthropic/`、`openai-responses/`），与 REQ-06 的 `<gw>/claude/<provider>`
及既有 `<client>/<provider>/<rest>` 结构冲突。修正为**客户端名作前缀 + 一张"前缀 → 期望线格式"表**：

| 路由前缀 | 期望线格式 | 客户端 | 适配器写入的 base |
|---|---|---|---|
| `claude` | `anthropic-messages` | Claude Code | `<gw>/claude/anthropic` |
| `codex` | `openai-responses` | Codex | `<gw>/codex/openai/v1` |
| `promptfoo` | `chat` | promptfoo | `<gw>/promptfoo/openai/v1` |
| `opencode` / `dsh` / `delphi`（既有） | `chat`（不强制，按内容吻合） | 既有客户端 | 不变 |

**"受管路由"的明确定义**（fail-closed 的 blast radius，R2 要求写死）：

> 受管路由 = `WIRE_ROUTE_PREFIXES` 的键集合 ∪ `CANARY_MANAGED_ROUTES` 的路由键集合，
> 二者**并集**即 fail-closed 的作用域。

未命中该并集的路径（含用户自建前缀）仍会被扫描与记录，但不因识别/覆盖失败而阻断——这是刻意保留的
"接得住但不打死"边界，并写进 `docs/KNOWN-ISSUES.md`。
