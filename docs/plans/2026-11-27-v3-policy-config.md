# v3 策略可配置化：边界方案

- 日期：2026-11-27
- 状态：**待评审**
- 前置：v0.10.9

## 问题

v3 的第一项交付是「策略引擎可配置化：per-checker `verdict → action` 用户可配」。
路线图原文还包括「新增 `redact`（非流式改写；流式仍不可执行）」。

但当前代码里有一条硬约束：

```typescript
// src/checkers/dangerous-command-scan.ts:119
// 语义封闭 → 唯一允许阻断的规则（见 Rule.blocking）。
blocking: true,
```

**`credential-file-read` 是全系统唯一有阻断权的规则。**

一旦开放配置，用户可以把它的 `finding → block` 改成 `finding → warn`，
等于**用一行配置关掉整个网关唯一的实质性防护**。

这不是理论风险。这个项目已经出现过两次"规则误报打断开发会话"
（powershell-download-exec、credential-file-read）。用户被误报折磨几次之后，
最自然的反应就是把规则调成 warn——而那正好把防线拆了。

## 核心判断：区分「偏好」与「安全基线」

配置项不是同质的。我按"改动后果"分三类：

| 类别 | 含义 | 例子 | 可否配置 |
|---|---|---|---|
| **A. 偏好** | 改的是观感，不改防护 | 某条观测类规则的 warn 措辞、evidence 保留条数 | ✅ 完全可配 |
| **B. 降级** | 降低某类检测的敏感度 | 观测类 checker 的 `finding → allow` | ⚠️ 可配，但必须留痕 |
| **C. 关闭** | 让唯一阻断规则失效 | `credential-file-read` 的 `finding → warn/allow` | ❌ **禁止** |

**C 类是本方案的全部重点。**

## 方案：阻断规则不可降级

### 判据（机械可断言）

> 任何 `safetyClass === true` 的 checker，其 `finding` 的 action **必须**仍是 `block`。
> 配置文件里若出现降级该动作的条目，**加载时即拒绝**（fail-fast，不是运行时忽略）。

理由：静默忽略最危险——用户以为配置生效了，实际没生效，或者反过来。
启动时报错逼他面对这个决定。

### 逃生舱（必须有，但要贵）

硬禁止会让人绕过它（改代码、改 fork）。给它一个**明确昂贵**的通道：

```jsonc
{
  "schema_version": 1,
  "acknowledged_risks": [
    {
      "rule_id": "credential-file-read",
      "action": "warn",
      "reason": "误报太多，暂时降级",          // 必填，不能为空
      "expires_at": "2026-12-31T00:00:00Z"   // 必填，最长 90 天
    }
  ]
}
```

三条约束：

1. **必须写明理由**（空字符串拒绝）
2. **必须有过期时间**（未给或超过 90 天拒绝）
3. **每次启动把降级状态写进 evidence** 并在 `doctor` 里显示为 `[WARN] degraded:*`

理由：这个项目处理的是**凭据出境**。降级是用户的权利，但必须是**有意识的、
临时的、可审计的**，而不是某天随手改配置忘了改回来。

**为什么设 90 天上限**：没有上限的话，写 `2099-12-31` 就等于永久关闭，
那和没有这条约束一样。90 天够覆盖任何"临时"场景，且逼用户重新面对决定。

## 与路线图的差异（需要拍板）

路线图写的是「per-checker `verdict → action` 用户可配」——**无限制**。
本方案加了 C 类禁止。

这是**收窄范围**，按 v1 的分期纪律（"能力缺口必须写进登记表，而不是靠总体目标含糊带过"），
这个收窄必须显式记录，不能悄悄做。

## `redact` 的定位

路线图要新增 `redact`（非流式改写）。它是**增强**而不是配置项：

- 它只在 `allow` 与 `warn` 之间有区别（观察到敏感内容 → 改写而非放行）
- 它**不**触及阻断路径：`redact` 不是 `block` 的替代
- 流式上物理不可执行（已转发字节不可撤回），保持现状

## 配置优先级

路线图要求「全局配置 > 项目级优先级」。我建议：

```
内置默认  <  全局 (~/.config/llmveto/policy.json)  <  项目级 (.llmveto/policy.json)
```

越靠近项目的越具体，覆盖全局。但**C 类禁止在两层都生效**——
项目级不能解除全局的禁止。

## 验收

| AC | 判据 |
|---|---|
| AC-1 | 配置降级 `credential-file-read` 而未写 `acknowledged_risks` → **加载失败**并说明原因 |
| AC-2 | `acknowledged_risks` 缺 `reason` 或为空 → 加载失败 |
| AC-3 | `expires_at` 缺失 / 已过期 / 超 90 天 → 加载失败 |
| AC-4 | 合法的降级 → 加载成功，evidence 记录降级事件，`doctor` 显示 WARN |
| AC-5 | 项目级配置**不能**覆盖全局的 C 类禁止 |
| AC-6 | 观测类 checker 的降级（B 类）无需 `acknowledged_risks`，但记 evidence |
| AC-7 | 过期的 `acknowledged_risks` 在启动时重新变为禁止（不是继续生效到下次重启） |

## 不做

- 不做**规则自身的开关**（`enabled: false`）。理由：那比降级更彻底，且用户有
  `acknowledged_risks` 已足够表达"我不想要这条"。
- 不做运行时热重载。配置变更需要重启——降级这种事不该在会话中途悄悄生效。

### 自审：我自己的方案最可能错在哪

按"这个方案最不合理的地方"排序：

1. **90 天硬上限是否武断**：用户如果确实需要长期降级（比如某规则对他们环境永远误报），
   每 90 天被强制改配置一次是纯粹的摩擦。反驳：摩擦正是设计意图——但"永远误报"这个
   情形真实存在，而本方案没有"彻底删除某规则"的合法路径（我明确不做 `enabled: false`）。
   这是个真实缺口。
2. **C 类禁止可能过度保护**：如果用户很清楚自己在做什么（比如他们根本不在 agent 里
   处理凭据），禁止降级就是家长式设计。反驳：`doctor` 的 WARN + evidence 已经足够
   告知，但"告知"不等于"阻止"。
3. **fail-fast 可能伤可用性**：配置有一个字段写错，网关起不来。在用户被误报困扰时，
   一个起不来的网关比一个降级过的网关更糟——他可能干脆不用了。

### 因此增加一条（自审结论）

**AC-8**：配置加载失败时，网关以**内置默认策略**启动（不降级），并在 `doctor` 与
stderr 同时报告"配置加载失败，已回退默认"，而不是拒绝启动。

理由：安全网关的核心价值是"它在拦"，而不是"它的配置正确"。配置错误不该导致
防护消失——而"起不来"会让人直接放弃使用。

这条与最初的 fail-fast 相反，是我在自审时推翻自己的判断。
